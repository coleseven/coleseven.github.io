Modeling the Traffic Camera Recorder

  • VBA
  • Excel
  • Monte Carlo simulation
  • Discrete-event simulation
  • Triangular distribution
  • Inverse-transform sampling
  • Traffic / load modeling

Overview

This is a discrete-event Monte Carlo simulation, built in Excel and VBA, of my Traffic Camera Recorder program — the program that captures 35 public traffic cameras and compiles them into daily videos. The recorder has gone through two shipped versions and a proposed third, and I built this simulation as my final project for a Modeling & Simulations course to answer a real engineering question: did each version actually make a meaningful improvement, and could the design be tuned further?

Problem / Goal

Rather than build the proposed third version of the recorder blind, I wanted to measure it first. The three designs are:

  • V1 — parallel: all 35 cameras polled on their own thread every ~3 seconds. Simple, but it spiked network traffic on every poll and captured many duplicate images.
  • V2 — grouped / phase-offset: cameras split into groups; within a group each camera polls at a small offset from the previous one, spreading the load over time.
  • V3 — conditional GET (proposed): V2 plus a conditional GET, so a re-poll that returns an unchanged image is not downloaded again.

Approach

Each version is a discrete-event model driven by two triangular distributions I fit from data I collected off the live cameras: inter-post time (how often a camera posts a new image) and image size. I wrote the whole thing in VBA rather than dragging spreadsheet formulas so the simulation could be dynamic — add or remove cameras, change group size, adjust the poll interval — without rebuilding the sheet each time. Random draws come from a triangular distribution implemented by inverse-transform sampling, and runs are seeded for repeatability. I measured each version with five metrics — capture efficiency, duplicate rate, poll efficiency, bytes per capture, and a waste factor — plus a bytes-downloaded-over-time series to visualize how bursty the traffic was.

Results

Across a run of 100 posted images per camera, the simulation confirmed both design changes were worthwhile:

  • V1 → V2 flattened the traffic. The bytes-over-time series dropped from ~700,000-byte spikes on every poll to a much smoother ~200,000-byte average — exactly the problem V2 was meant to solve. The summary metrics were otherwise nearly identical (capture efficiency about 0.01 lower, a direct cost of the offset).
  • V2 → V3 roughly halved the data. The conditional GET drove the duplicate rate from ~0.50 to 0 and cut total bytes downloaded from ~1.2 billion to ~600 million, with bytes-per-capture nearly halved. That confirmed the proposed V3 change is worth building.
  • Tuning: following the rule offset = poll interval / cameras per group keeps the system well-behaved (a group size of 4 worked best). No offset or group-size choice improved the headline metrics beyond that — but violating the rule makes V2 noticeably worse, degrading back toward V1's bursty behavior.

What I Learned

The biggest lesson was about scope and structure. Converting my formula-driven sheet into dynamic VBA was the right call, but I paid for a weak initial design — I hadn't built the first file to be extended into the later versions, so I had to rebuild parts of it, and I referenced hard-coded cells instead of named ranges (something I'd never skip again). On the modeling side, I learned where my simulation was honest and where it was a simplification: using one shared distribution for every camera, rather than a per-camera "personality", is the main thing I'd fix to make the results line up more closely with the real program.
