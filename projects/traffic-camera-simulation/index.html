Overview

This project comes in two parts. The first is the program itself; the second is the simulation I built to study that program as it evolved. The program takes images from public traffic cameras in the Beaufort area and compiles them into a video each day.

Program Progression

The first version (V1) downloaded images from 35 different cameras in parallel, polling every 2 seconds and downloading one image per camera each time. V1 worked, but it had two problems: it generated a large traffic spike every 2 seconds, and it captured a lot of duplicate images. Its unique-image capture rate was roughly 99%. The second version (V2) split the cameras into groups, with a small phase offset between each camera in a group — the first camera polls, the second polls a few seconds later, and so on through the group. This smoothed out the big traffic spikes from V1, at the cost of a very slight drop in capture efficiency (down to about 98%) caused by the offsets. The third version (V3) is one I've been planning to implement: it adds a conditional GET to check whether an image being downloaded is unique or a duplicate, and skips the download if it's a duplicate. V3 doesn't exist yet, but I studied it in my simulation.

Hardware and Automation

On top of writing the software, I also built a PC to run this program 24/7. It runs on a Windows 10 machine — I would have preferred Linux, but the person I built it for wanted Windows. I won't go deep into the specs, but the important part is that it has a 256 GB SSD and a 6 TB HDD. The program is actually two separate programs: a recorder and a compiler. The recorder runs on the CPU, and the compiler uses ffmpeg GPU encoding. Both are scheduled with .bat scripts and the Windows Task Scheduler. The recorder script runs 24/7, and every hour a small .bat script checks that it's still running and restarts it if it isn't. Every night at 11:59, the compiler script runs and compiles all of the previous day's images. It also cleans up after itself: it deletes the images once they've been compiled, and if there are more than 90 days of compiled videos it deletes the oldest one.

The recorder downloads images onto the SSD, and the compiler then compiles them and writes the finished file to the HDD. This split matters for a couple of reasons. First, the SSD's read/write speed is higher than the HDD's, and when you're compiling 35 videos — each made from a full 24 hours of images captured roughly every 3 seconds — slow read/write really adds up. Second, it let me cut the cost of the PC for my client, since I only needed one smaller SSD plus a HDD instead of all SSDs. Finally, the whole thing runs on boot: the PC auto-boots as long as it has power (and the CMOS battery hasn't died).

Simulation

For my final project in Modeling and Simulations, I chose to study this program to see whether my V2 update actually made meaningful improvements, and whether my potential V3 change would too. I built the simulation in Excel and VBA, using data I'd gathered with small Python helper scripts to determine how often images actually post and the average size of each image. I created three separate Excel sheets, one for each version of the program (all included in the GitHub repository). For a full breakdown of the simulation, its metrics, and the results, see the dedicated Modeling the Traffic Camera Recorder project.

Results

The simulations showed that from V1 to V2, the bursty traffic of V1 was smoothed out in favor of a much steadier V2. From V2 to V3, the conditional GET was very beneficial — it drives the duplicate rate to zero. That's genuinely useful, because it means I can add more cameras to the program without having to upgrade the hardware.
