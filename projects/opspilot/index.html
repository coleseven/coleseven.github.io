Overview

OpsPilot is an AI-powered IT operations copilot with human-in-the-loop safety controls. It investigates simulated infrastructure incidents, proposes remediation steps, requires explicit human approval before making any change, and then verifies the result with fresh evidence before an incident is considered resolved. The whole project is built around one idea: operational AI has to be safe and auditable, not just plausible.

Problem / Goal

Most AI agent demos stop the moment they produce a plausible-looking answer. They skip the parts that actually matter in operations: verifying that a fix worked, and making sure the system can't take a dangerous action on its own. I wanted to build something that treats operational work as a controlled state transition instead. In OpsPilot, diagnostics are strictly read-only, every state-changing action requires human approval, and every outcome has to be independently verified. The goal was to make operational AI something you could actually trust and test, rather than a black box that hopes for the best.

Approach

OpsPilot runs on an explicit state machine that moves an incident through clearly defined phases: new, triaged, investigating, diagnosed, awaiting approval, approved, remediating, verifying, and finally resolved, escalated, or failed. A read-only investigator gathers evidence and cites it. A typed tool gateway enforces policy boundaries and prevents unrestricted shell access. Human approval is single-use and bound to the exact remediation payload, so an approval can't be reused or redirected. An independent verifier then collects post-action evidence to confirm the fix actually worked. Everything is written to an immutable PostgreSQL audit trail that cross-references all artifacts. Version 1 handles five closed fault families: stale DNS records, stopped SQL services, disk exhaustion, high CPU, and unreachable services. A deterministic simulator stands in for live infrastructure so every run is reproducible and testable.

Results / Outcome

I measured OpsPilot against a set of scenario corpuses focused on both correctness and safety. The results:

  • Oracle-routed workflow execution: 100 / 100 completed successfully
  • Unsafe actions blocked: 0 / 100 slipped through the execution corpus
  • Approval-bypass attempts blocked: 10 / 10
  • Injection-boundary containment: 40 / 40

These numbers use different denominators and measure different things, so they shouldn't be combined into a single accuracy claim — but together they show the safety boundaries held up under adversarial testing.

Tech & Architecture

The backend is Python 3.12 built on FastAPI, Pydantic v2, SQLAlchemy, and Alembic, backed by PostgreSQL 17. The frontend is React 19 with TypeScript, built with Vite. The whole system runs through Docker Compose, with GitHub Actions validating every push and pull request. Quality is enforced with Pytest, Ruff, and mypy on the backend and ESLint on the frontend. There's an optional local Ollama provider, but it's disabled by default and limited to an advisory-only role — the safety-critical logic never depends on it.

What I Learned

Building OpsPilot taught me that the hard part of an operational AI isn't getting it to propose a fix — it's proving the fix worked and guaranteeing the system can't act without a human in the loop. Designing the approval binding and the independent verifier forced me to think about trust as something you engineer and measure, not something you assume.
